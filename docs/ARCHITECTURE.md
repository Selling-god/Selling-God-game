# 구조와 설계 경계

## 흐름
```
브라우저
  ├─ HTTPS: 페이지·도트 그림·공개 설정
  ├─ HTTPS → Supabase Auth: 로그인, 갱신, 이메일 연결
  └─ WSS → Render Node 서버
                ├─ 토큰 → Supabase Auth /user 검증
                ├─ 20Hz 권한 있는 게임 시뮬레이션
                ├─ 기본 6Hz 플레이어별 주변 상태 전송
                └─ 서버 전용 key → Supabase PostgREST 저장
```
한 HTTP 서버가 정적 파일과 `/socket`을 함께 제공합니다. CORS 프록시나 별도 프런트 도메인이 필요하지 않습니다.
클라이언트는 이동 의도, 대상, 기술, 구매/제작 요청을 보냅니다. 좌표·골드·레벨 상태를 클라이언트가 최종 결정하지 않습니다.

## 핵심 구현
- 공유 시드 월드: 클라이언트와 서버가 같은 충돌 그리드를 만듭니다. 서버가 실제 이동을 확정합니다.
- 이동: 대각선 정규화, 320ms 입력 만료, 충돌 substep, 서버 A* 클릭 이동, 클라이언트 표시 예측/보정.
- 전투: 서버 거리·시야·해금·마나·쿨타임 검사. 피해량과 보상 RNG는 서버에 있습니다.
- 보스: 공격 전 예고 도형을 보내고, 종료 시점의 플레이어 위치로 피격을 판정합니다.
- 보상: 기여자 기록과 인접 파티 조건에 따라 각자 보상. last-hit 독점 보상이 아닙니다.
- 저장: 사용자별 비동기 저장 큐로 같은 프로세스에서 쓰기 순서가 뒤집히지 않도록 합니다.
- 무결성: 거래/의뢰 요청 nonce 캐시, 유효 수량·소유·레벨·NPC 거리 확인.
- 채팅: 메모리에서 전달, 글자수와 전송 빈도 제한, UI는 HTML을 escape합니다.
- 데이터 범위: 다른 플레이어의 이름/직업/레벨/HP/위치 등 공개 상태만 전송합니다.
- 네트워크: heartbeat, 재접속 backoff, 처리하지 못한 요청 취소, backpressure 시 상태 프레임 생략.
- 압축: 1KB 이상 스냅샷의 permessage-deflate. context takeover 비활성, 압축 작업 동시성 4.
- 화면: 가림막 투명화, 근접 대상 선택, 보행 프레임, 스킬·피해·전리품·보스 공격 경고.
- 서버 다운 시 싱글 플레이로 조용히 전환하는 코드가 없습니다.

## 영속 범위와 원자성
캐릭터 저장 JSON은 한 행으로 upsert합니다. 브라우저에는 service key가 전달되지 않습니다.
한 프로세스의 요청 nonce·저장 큐는 재시작 후 유지되지 않습니다.
이 구조는 단일 프로세스 초기 게임용이며 다중 서버 트랜잭션 시스템이 아닙니다.
파티·몬스터·채팅은 휘발성 상태입니다. 재시작 시 필드는 초기화됩니다.

초기 버전은 정상 종료/접속 해제/주기/주요 행동 뒤 저장을 시도합니다.
갑작스러운 프로세스 종료 및 저장 장애 시 마지막 성공 저장 이후의 손실 가능성이 있습니다.
결제나 유료 아이템을 연결하기 전에 별도의 감사 원장, 원자적 거래, 운영 백업을 설계해야 합니다.

## 성능 해석
24명은 기본 설정과 로컬 짧은 부하 검사의 대상일 뿐 서비스 수준 보장이 아닙니다.
Render 인스턴스의 CPU/RAM, 연결 지연, 외부 인증/저장, 대역폭 한도가 실제 체감에 영향을 줍니다.
입력 전송률/스냅샷 주기/보이는 범위/압축을 변경할 때 이동 품질과 CPU를 함께 측정하세요.

## 확장하려면
영구 길드·거래·경매장에는 정규화 테이블과 서버 트랜잭션이 필요합니다.
다중 월드에는 월드별 프로세스 라우팅, 계정 연결 소유권, 분산 저장 revision 또는 락이 필요합니다.
대규모 운영에는 가입 봇 방어, 모더레이션, 신고·차단·제재, 장애 감지, 백업/복구, 관측 지표가 필요합니다.
이 초기 버전이 이 기능들을 이미 제공한다고 해석하지 마세요.
